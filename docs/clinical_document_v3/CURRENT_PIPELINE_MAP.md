## 7. Document ingestion pipeline — end-to-end trace

Entry point: `backend/app/main.py::process_upload_job(job_id)` (line 1302), a background job runner. Order of operations:

1. Load `UploadJob`, `User`, `Patient`; mark job `processing`.
2. **Security scan** (`app/services/security_scan.py::run_security_scan`) — blocks processing on an explicit malicious verdict; `scan_unavailable` never blocks.
3. **SHA-256 duplicate detection** (Level 1) — `compute_sha256`; if an existing `Document` with the same `patient_id` + `file_sha256` exists, job short-circuits to `status="duplicate"`, no new Document/LabResult is ever created.
4. **Classification** (only if `job.section == AUTO_CLASSIFY_SECTION`): tries real Reducto Classify+Split concurrently (`reducto_extraction.classify_and_check_split`); on `ReductoError` falls back to `LegacyExtractionProvider` (plain-OCR + keyword classifier). A Reducto Split "mixed" result triggers `_finish_mixed_reducto_upload` (creates parent + child Documents, see §1/§6) and returns early. Sets `job.document_type`/`classification_status`/`classification_confidence`/`classification_source`; a `needs_confirmation` status pauses the job.
5. **Extraction** — branches on `job.document_type`:
   - Reducto enabled AND `document_type == "laboratory_results"` → `reducto_extraction.build_pipeline_result_labs(reducto_file_id)`
   - Reducto enabled AND `document_type` in the 6 "reader" types → `reducto_extraction.build_pipeline_result_reader(...)`
   - Otherwise (Reducto unavailable/failed, OR `job.section == "discharge_summary"`) → falls through to the **legacy pipelines**:
     - `job.section == "discharge_summary"` → `discharge_summary_pipeline.process_uploaded_discharge_summary` (see §8)
     - else → `document_pipeline.process_uploaded_document` (see below)
6. **Patient identity check** (`patient_identity.check_patient_identity`) — `matched|needs_confirmation|mismatch|insufficient_identity|matched_override`. `mismatch` creates a **quarantined Document** (`patient_id=None`, `intended_patient_id=patient.id`, `review_status="quarantined"`) and stops. `needs_confirmation` pauses the job (nothing persisted).
7. **Document row creation** (`main.py:1681-1732`) — all identity/report/lab-name/date fields copied from `parsed_data`; `note_body` = `pipeline_result.get("note_body") or parsed_data.get("note_body") or extracted_text`; `parsed_content` = JSON-dumped `pipeline_result["parsed_content"]` if present.
8. **LabResult + SourceEvidence creation loop** (`main.py:1749-1835`) — for each row in `labs`: builds a `LabResult` from whatever the extraction stage already computed (`canonical_name`, `normalization_confidence`, `normalization_method` etc. are NOT recomputed here — they're carried through verbatim from step 5's output). Level-3 duplicate-observation linking (`duplicate_of_lab_result_id`) runs here. `SourceEvidence` is created per lab row from `lab.get("evidence")` (only present for Reducto-extracted rows) or a synthesized `source_text` string for legacy rows (no bbox).
9. **Phase 4 structured reader extraction** (`main.py:1885-1924`) — only for the 6 reader document types; reuses Reducto's reader result if present, else calls `structured_reader_service.extract_structured_sections` (OpenAI). Writes JSON to `document.structured_sections`. Best-effort; failure never fails the upload.
10. `job.status = "done"`.

**`backend/app/services/document_pipeline.py::process_uploaded_document`** (the *legacy* — non-Reducto — extraction path, called only when `section != AUTO_CLASSIFY_SECTION` or Reducto declined/failed) handles exactly two cases:
- `section == "bloodwork"` → `process_bloodwork_document`: runs Google Document AI table parsing (`parse_labs_from_google_extraction`) → `extract_google_labs`, then conditionally (`lab_rows_need_ai_help`) falls back to an OpenAI vision organizer (`ai_lab_organizer.organize_labs_with_ai`) and merges (`merge_lab_results`).
- anything else → `empty_parsed_document(section)` (no labs, no discharge parsing).

**Important finding:** `document_pipeline.py:12` imports `parse_discharge_document` from `app/parsers/discharge_summary_parser.py` but **never calls it anywhere in the file** — this is a dead/unused import; `discharge_summary_pipeline.py` (a completely separate module, §8) is the actual discharge code path, invoked directly from `main.py`, not through `document_pipeline.py`.

**CBC vs non-CBC handling (legacy pipeline only)** — `document_pipeline.py::standardize_lab_row_shape`/`normalize_rows_preserving_cbc`: any row whose raw name matches one of 27 hardcoded CBC abbreviations (`CBC_EXACT_LABELS`, e.g. `WBC`→`"White Blood Cell Count"`) is assigned its canonical/display name directly from that hardcoded dict and **never passed through `lab_catalog.normalize_lab_rows` or `lab_resolver.resolve_analyte` at all**. Every non-CBC row IS passed through `lab_catalog.normalize_lab_rows` (→ `find_lab_definition`), but this legacy path **never calls `lab_resolver.resolve_analyte`/`resolve_test_name_dict`** either — see §9 for why this matters for canonical-name-format consistency.

**The Reducto path is different:** `reducto_extraction.py::extract_lab_results` (line 406-488) calls `lab_resolver.resolve_test_name_dict` (line 455) for **every** row uniformly — there is no separate CBC-vs-non-CBC branch in the Reducto path at all.

## 8. `discharge_summary_pipeline.py` — full read

`backend/app/services/discharge_summary_pipeline.py`, entry point `process_uploaded_discharge_summary(file_path, filename)` (line 767).

- Renders each PDF page to a PNG (PyMuPDF/`fitz`, `PDF_RENDER_ZOOM=2.6`) and extracts the PDF's native text layer per page; falls back to Google Document AI OCR per-page when native text is ≤80 chars.
- Sends each page **in parallel** (`ThreadPoolExecutor`, `MAX_PARALLEL_PAGES=3`) to OpenAI (`responses.create`, model from `OPENAI_DISCHARGE_LAYOUT_MODEL` env, default `gpt-4.1`) with a verbatim-transcription system prompt — explicitly instructed to copy every word, never summarize/truncate, and classify each block into one of a fixed 13-key `ALLOWED_SECTION_KEYS` set (`administrative_information`, `diagnoses`, `discharge_status`, `epicriza`, `investigations`, `consults`, `laboratory_normal`, `laboratory_abnormal`, `treatment_in_hospital`, `recommended_treatment`, `prescriptions_released`, `recommendations`, `other`).
- Per-page JSON responses are merged across pages (`_merge_sections` — sections with the same key/title, or ones in a known "continues across pages" set, get concatenated).
- Produces a `payload` dict: `{document_type: "discharge_summary", extraction_mode, patient_name, cnp, date_of_birth, sex, admission_date, discharge_date, hospital_name, page_count, page_payloads, sections: [...], warnings}`.
- **Persistence**: the function returns `"note_body": json.dumps(payload, ensure_ascii=False)` — i.e. the ENTIRE structured payload (all sections + identity fields + warnings) is JSON-serialized into the single `Document.note_body` Text column (line 824). It does **not** use `Document.structured_sections` (that field is reserved for the 6 unrelated Phase-4 reader document types, §1/§9) and does **not** use `Document.parsed_content` (reserved for real Reducto Parse block data).
- `hospital_name` is extracted (`payload.get("hospital_name")`) and returned in the pipeline result dict, but **`Document` has no `hospital_name` column** — inspecting `main.py`'s `document = models.Document(...)` construction (`main.py:1681-1732`) confirms `hospital_name` is never assigned to any Document field; it only survives inside the `note_body` JSON blob.
- **Does not create any `PatientEvent` row** (no import/usage of `models.PatientEvent` anywhere in this file — confirmed by grep).
- **Does not create any `LabResult` row** — `laboratory_normal`/`laboratory_abnormal` sections are transcribed as verbatim TEXT inside a section body, never parsed into structured `LabResult` rows. (Contrast with the separate `bloodwork` pipeline, §7, which does produce `LabResult` rows.)
- A companion service file, `backend/app/services/discharge_layout_formatter.py`, exists in the services directory but **grep confirms it is imported nowhere in the backend** — it is dead code. The frontend has its own separate client-side formatter, `frontend/lib/discharge-epicriza-formatter.ts::formatPdfLikeDischargeText` (§15), doing similar text-layout formatting independently.

## 9. Lab extraction/normalization — three independent catalogs

Three genuinely separate alias/canonicalization systems exist, with **three different canonical-name string formats**:

1. **`backend/app/synonyms.py`** — `LAB_DEFINITIONS = CBC_TEST_DEFINITIONS + EXTRA_LAB_DEFINITIONS` (line 557). Each entry: `{canonical_name, display_name, short_name, category, synonyms}`. `canonical_name` format is a **lowercase snake_case slug**, e.g. `"wbc"`, `"hemoglobin"`, `"hematocrit"`, `"free_t4"`. `normalize_test_name(raw)` (line 628) does exact/substring synonym matching against this list; unresolved rows get `canonical_name = normalized_raw.replace(" ", "_")`.

2. **`backend/app/services/lab_catalog.py`** — `LabDefinition(canonical_name, category, synonyms)` dataclass, `LAB_DEFINITIONS: list[LabDefinition]` (line 125+). `canonical_name` format is a **human-readable Title-Case English phrase**, e.g. `"White Blood Cell Count"`, `"Platelet Count"`. `find_lab_definition(raw_name)` (line 870) does scored exact/compact-key/substring matching (no fuzzy/OCR tolerance). `normalize_lab_row`/`normalize_lab_rows` (line 966/1004) wrap this to add `test_name`/`canonical_name`/`category` onto a raw row dict, defaulting unmatched rows to `category="Alte analize"` and `canonical_name=raw_name` verbatim.

3. **`backend/app/services/lab_resolver.py`** — `resolve_analyte()` (line 477, see §10) is a **wrapper/superset**, not a third independent catalog: it builds its own `_CANDIDATES` universe (`_build_candidate_universe`, line 256) by combining BOTH of the above catalogs' alias lists, then tries, in order: (1) `synonyms.normalize_test_name` unchanged (→ snake_case canonical form), (2) `lab_catalog.find_lab_definition` unchanged but re-keyed through `lab_catalog.compact_key()` into a **lowercase, no-space/no-punctuation compact slug** (e.g. `"whitebloodcellcount"`, NOT lab_catalog's own `"White Blood Cell Count"` form), (3) only if both fail, its own OCR-confusion-aware fuzzy Levenshtein scoring across the combined alias universe (weighted edit distance with reduced cost for known OCR-confusable glyph pairs like v/w, i/l/1, o/0, s/5, b/8, plus the "rn"↔"m" bigram confusion).

**Real ingestion call-site divergence** (confirmed by grep + reading both pipelines):
- The **legacy bloodwork pipeline** (`document_pipeline.py`, §7) uses `lab_catalog.normalize_lab_rows`/`find_lab_definition` for non-CBC rows, and its own hardcoded `CBC_EXACT_LABELS` dict for CBC rows — it **never calls `lab_resolver.resolve_analyte`/`resolve_test_name_dict`**, so `LabResult.normalization_method` for rows from this path is never actually set to `"exact"|"alias"|"ocr_fuzzy"` (those method strings are `lab_resolver`'s vocabulary) — `lab.get("normalization_method")` at `main.py:1765` is simply whatever `document_pipeline.py`'s row dict happened to carry (nothing in that module sets this key at all, so it is `None` for the legacy path).
- The **Reducto lab-extraction path** (`reducto_extraction.py::extract_lab_results`, §7) calls `lab_resolver.resolve_test_name_dict` for every row, which DOES set `normalization_confidence`/`normalization_method` to the `lab_resolver` vocabulary (`exact|alias|ocr_fuzzy|vendor_specific|text_matched_unverified|unresolved`), and produces `canonical_name` in lab_resolver's re-keyed **compact-slug** format for stage-2 matches, or synonyms.py's **snake_case** format for stage-1 matches.
- The **FHIR interop connector** (`app/services/interop/fhir_connector.py:420`) also calls `resolve_analyte` directly.

The net effect (documented explicitly in `ask_bragi/tools.py`'s `_canonical_lab_filter` docstring, §12) is that **`LabResult.canonical_name` in the live database is stored in at least two incompatible formats depending on which pipeline/era ingested a given row** — a human-readable form (`"Platelet Count"`) from the legacy path vs. a snake_case slug (`"platelet_count"`) from the resolver path — neither of which is a plain substring of the other.

## 11. Document / patient deletion behavior

**`DELETE /documents/{document_id}`** — `backend/app/api/routers/documents.py:1056-1100` (`delete_document`):
1. Authorization check (`can_access_patient`; patients additionally must own the document).
2. Explicitly bulk-deletes `NoteDocumentLink` rows referencing this document (either direction) — `synchronize_session=False`.
3. Explicitly bulk-deletes `DoctorDocumentReview` rows for this document.
4. Explicitly bulk-**updates** `UploadJob.document_id` → `NULL` for jobs pointing at this document (detach, not delete).
5. `db.delete(document)` then `db.commit()` — relies on the ORM-level cascades declared on `Document` (`lab_results` cascade `all, delete-orphan` → cascades further to each `LabResult.source_evidence`; `audit_logs` cascade `all, delete-orphan`) to remove those rows automatically.
6. Deletes the file at `document.saved_to` from disk (best-effort, swallows exceptions).

**Not explicitly handled in this route**: `SharedStructuredPage.document_id` (no ORM cascade declared on `Document` for it), `AskBragiConversation.document_id` (no ORM cascade), and any `Document.parent_document_id` children (relies entirely on the DB-level `ondelete="SET NULL"` declared on that column) or `SourceEvidence` rows with `lab_result_id IS NULL` (document-level evidence, §12 — no `LabResult` to ride a cascade through, and no ORM cascade from `Document` directly to `SourceEvidence` exists — only `LabResult.source_evidence` cascades). This single-document delete path does not appear to defensively clear document-level `SourceEvidence` the way the patient-account-deletion path does (see below) — see Open Questions.

**`DELETE /my/account`** (patient role) — `backend/app/api/routers/patients.py:727-897` (`delete_my_account`), for the `patient` branch specifically (lines 749-897), in order:
1. Collects every `Document` where `patient_id == patient.id` **OR** `intended_patient_id == patient.id` (this second clause explicitly includes identity-mismatch-quarantined documents that were uploaded FOR this patient but never linked via `patient_id`).
2. Bulk-deletes `SharedStructuredPage`, `DoctorDocumentReview`, `UploadJob` rows referencing those document ids.
3. **Explicitly bulk-deletes `SourceEvidence` rows for those document ids** — the code comment explains why this is necessary here but not automatic: `LabResult.source_evidence` does cascade (so lab-linked evidence is cleared when its `LabResult` cascades via `Document.lab_results`), but **document-level evidence** (`lab_result_id IS NULL`, created by `_ensure_document_level_evidence`, §12) has no `LabResult` to ride that cascade through, and would otherwise raise a `ForeignKeyViolation` — this was reproduced against both local and production before the fix.
4. Comment confirms `Document.parent_document_id` and `LabResult.duplicate_of_lab_result_id` are both **`ON DELETE SET NULL` at the DB level** (applied by the legacy `run_migrations()` / `alembic/versions/0001_legacy_baseline.py`), so no manual clearing is needed for those two self-referential FKs.
5. Deletes remaining `UploadJob` rows for the patient with no `document_id` set.

## OPEN QUESTIONS FOR PHASE 3+

Factual observations only — no design recommendations:

1. **No existing field on `Document` is a general-purpose structured-section schema.** Three different mechanisms currently exist for "structured content beyond `extracted_text`": `structured_sections` (JSON `{language, sections: {key: text}}`, used only for 6 reader document types), `parsed_content` (JSON Reducto Parse blocks), and `note_body` (used both as plain text for `notes`/legacy documents AND as an entire discharge-summary-specific JSON payload for `discharge_summary`, distinguished only by the frontend's `JSON.parse` + shape check at runtime, not by any schema/type column).

2. **`Document` has no `hospital_name` column.** `discharge_summary_pipeline.py` extracts a `hospital_name` per document, but it is never persisted as a queryable field — it only exists inside the `note_body` JSON blob for documents that happen to be discharge summaries.

3. **Three incompatible canonical lab-name formats coexist in the live `lab_results.canonical_name` column** depending on which era/pipeline ingested a given row: snake_case slugs (`synonyms.py`/stage-1 resolver matches), Title-Case English phrases (`lab_catalog.py`/legacy non-CBC path), and a third compact-slug re-keying of `lab_catalog.py`'s own names produced only by `lab_resolver.py`'s stage 2 (e.g. `"whitebloodcellcount"`). `ask_bragi/tools.py::_canonical_lab_filter` works around this by trying all three forms per query rather than the database being consistent.

4. **CBC rows never pass through either alias catalog in the legacy (non-Reducto) bloodwork pipeline** — they get their canonical/display name from a fourth, independent hardcoded dict (`document_pipeline.py::CBC_EXACT_LABELS`), which happens to produce the same string format as `lab_catalog.py` but is a maintained-in-parallel, separate source of truth.

5. **`document_pipeline.py` imports `parse_discharge_document` from `discharge_summary_parser.py` but never calls it** — dead import; the real discharge pipeline is the entirely separate `discharge_summary_pipeline.py`, invoked directly from `main.py`.

6. **`backend/app/services/discharge_layout_formatter.py` is dead code** (imported nowhere in the backend) while an independent, differently-implemented formatter (`frontend/lib/discharge-epicriza-formatter.ts::formatPdfLikeDischargeText`) performs comparable text-layout formatting client-side.

7. **`Document.original_layout` (as read by `main.py::get_document_payload` via `getattr(document, "original_layout_json", None)`) is always `None`/`{}`** — `original_layout_json` is not a real column on the `Document` model (grep confirms no such column exists in `models.py`), so this `getattr` default always fires. The frontend discharge page nonetheless has a full `OriginalLayout`/`LayoutPage`/`LayoutBlock` type definition and `OriginalLayoutViewer` component built to consume this field — currently always empty in practice.

8. **`PatientEvent` (admissions/timeline) is entirely decoupled from document upload.** Uploading a `discharge_summary` document does not create, update, or link to any `PatientEvent` row — the two are populated through completely independent user actions (`POST /patient-events` vs. the upload pipeline). Any future feature that wants a discharge document to appear "on the timeline" automatically has no existing linkage to build on.

9. **`ask_bragi/tools.py::_tool_get_document`'s section-lookup only ever reads `structured_sections` or `extracted_text`** — it never reads `note_body` or `parsed_content`. For a discharge-summary document specifically, this means Ask Bragi's `get_document` tool sees the flattened `extracted_text` export of the discharge sections (produced by `_payload_to_text` at ingestion time), not the original per-section JSON structure stored in `note_body`, and not whatever a future structured-document schema might add.

10. **`DELETE /documents/{document_id}` (single-document delete) does not explicitly clear document-level `SourceEvidence` rows (`lab_result_id IS NULL`)** the way the patient-account-deletion path does — it relies only on the ORM's `Document.lab_results` cascade (which only reaches lab-linked evidence via `LabResult.source_evidence`). Whether this is a live bug (an orphaned/blocking FK) or safely covered by a DB-level cascade not visible in `models.py` was not verified against the actual Alembic migration history in this pass.

11. **`ask_bragi/tools.py`'s own inline comment about `PatientMedication.status` semantics** (`"active" | "discontinued" | other recorded status`) **does not match the actually-enforced status vocabulary** (`{"active", "as_needed", "paused", "stopped"}`, enforced in `medications.py`) — `"discontinued"` is not a real value in this codebase today.

12. **`SharedStructuredPage.document_id` and `AskBragiConversation.document_id` have no `ondelete` declared in `models.py`** and are not defensively cleared by the single-document `DELETE /documents/{id}` route (only the patient-account-deletion path explicitly bulk-deletes/detaches them) — actual DB-level constraint behavior for these two FKs on a lone document delete was not independently verified against Alembic migrations in this pass.

## SUMMARY — most architecturally significant findings for schema design

- `discharge_summary_pipeline.py` stores its entire structured output (sections, patient identity, warnings) as a single JSON blob inside `Document.note_body` — there is no dedicated structured-sections column for discharge summaries specifically; the unrelated `structured_sections` field is reserved for 6 other document types and is never populated for discharge summaries.
- `Document` already has a real parent/child relation (`parent_document_id`, self-FK, `ondelete="SET NULL"`) from Reducto Split, plus a separate, unrelated `NoteDocumentLink` many-to-many table — two different "documents relate to documents" mechanisms already exist for different purposes.
- There are (at least) three incompatible canonical lab-name formats live in `lab_results.canonical_name` today, papered over at query time by `ask_bragi/tools.py::_canonical_lab_filter` trying all of them rather than fixed at ingestion.
- CBC lab rows in the legacy (non-Reducto) pipeline bypass both alias catalogs entirely via a fourth hardcoded dict, while the Reducto pipeline runs every row (CBC or not) through the same `lab_resolver.resolve_analyte` fuzzy/OCR-aware resolver — the two ingestion paths are structurally different, not just differently configured.
- `Document.original_layout` (referenced by the frontend's discharge reader and `OriginalLayoutViewer` component) is dead on the backend — the column it reads (`original_layout_json`) doesn't exist on the model, so it's always empty.
- Ask Bragi's `get_document` tool never reads `note_body` — for discharge summaries it only ever sees the flattened `extracted_text`, meaning any new structured schema stored only in `note_body`/a new field would be invisible to Ask Bragi unless that tool is updated too.
- `PatientEvent` (the timeline/admissions table) has zero automatic linkage to document upload — a discharge summary upload today never creates or touches a `PatientEvent` row.
- The Ask Bragi right-workspace/chat frontend already has real ownership-guard and layout-toggle machinery in place (`justCreatedConversationIdRef`, `RightWorkspace`'s conditional-wrapper fix) that a new structured-document viewer would need to compose with, not replace.
- Document deletion cascades are inconsistent in coverage: the patient-account-deletion path explicitly handles several FK edge cases (document-level `SourceEvidence`, Ask Bragi conversations, interop identity links) that the single-document `DELETE /documents/{id}` route does not visibly replicate.
